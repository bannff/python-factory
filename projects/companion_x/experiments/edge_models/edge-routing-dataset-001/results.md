# Edge routing dataset readiness

**Tracking:** [ENG-204](https://linear.app/ditto/issue/ENG-204/define-outcome-grounded-edge-routing-dataset-and-evaluation-contract), child of [ENG-188](https://linear.app/ditto/issue/ENG-188/heterogeneous-edge-model-coordination-over-offline-ditto-peers).
**Status:** Contract and quality gates implemented locally. No reviewed live Ditto SDK route outcomes exist, so no training dataset or learned router has been published.

The Dataset `edge_routing_example` schema separates decision-time candidate features from the route actually attempted and its independently reviewed outcome. Materialization checks typed evidence bytes and digests, split isolation, duplicate identities, eligibility, time order, and live SDK outcome review. Train, validation, and test views are split-specific. The writer and public verifier refuse routing publication until a routing-specific sealed collector can attest the run and reviewer receipt. The current zero-record readiness call returned `status=no_labels`, `training_allowed=false`, and `reviewed_label_count=0`; the ENG-201 synthetic fault corpus is excluded from training and outcome metrics.

Test-only synthetic records exercise the contract and publication refusal. They do not measure route quality, task completion, Ditto synchronization, or device resource use. The next evidence gate is [ENG-205](https://linear.app/ditto/issue/ENG-205/attest-live-ditto-routing-outcomes-before-edge-router-training), following a licensed N=2 Ditto SDK run under ENG-184. It must bind actual task/claim/result attempts and independently reviewed outcomes to the sealed run. Only then can we freeze train, validation, and untouched test episodes and compare a tiny router with the deterministic selector under identical safety checks.
